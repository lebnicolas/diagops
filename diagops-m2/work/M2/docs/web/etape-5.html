Étape 5

Tester les contrôles eux-mêmes

Un contrôle qui ne signale rien peut être excellent — ou complètement cassé. Rien ne distingue les deux situations à l'œil. D'où 35 tests, sur un jeu de neuf lignes dont on connaît d'avance chaque anomalie.

Pourquoi tester un audit

C'est le paradoxe de tout dispositif de détection : le silence est ambigu. Quand une règle rapporte zéro échec, deux explications tiennent — les données sont saines, ou la règle est inopérante. Un nom de colonne mal orthographié suffit à rendre un contrôle définitivement muet.

La parade consiste à vérifier les deux directions :

  • cas invalide — on plante une anomalie connue, le contrôle doit la trouver ;
  • cas valide — on fournit une ligne saine, le contrôle doit se taire.

Le second est aussi important que le premier. Un contrôle qui crie au loup en permanence noie les vraies anomalies, et on finit par l'ignorer.

Le jeu d'essai

Neuf lignes en tout — trois équipements, trois événements, trois interventions — construites pour porter exactement les anomalies qu'on veut voir remonter : 

# criticité hors énumération + puissance négative
{"equipment_id": "EQ-2", ..., "criticality": "urgent",
 "rated_power_kw": -5.0},

# identifiant dupliqué + date sentinelle
{"equipment_id": "EQ-1", ..., "commissioning_date": "1900-01-01"},

# équipement contredit par l'événement + coût sans pièce + note avec email
{"maintenance_id": "MT-2", "event_id": "EV-1", "equipment_id": "EQ-2",
 "parts_cost_eur": 80.0, "parts_replaced_count": 0,
 "work_order_note": "Voir avec jean.dupont@example.com"},

Neuf lignes suffisent parce qu'on ne cherche pas à simuler la réalité : on cherche à savoir si chaque contrôle réagit à ce qui le concerne, et seulement à ça.

Ce que les tests vérifient

TestCe qu'il garantit
toutes les règles sont exécutées aucune règle déclarée au registre ne reste orpheline dans le code
anomalies plantées détectées chaque anomalie remonte, et avec le bon nombre d'occurrences
lignes saines silencieuses pas de faux positif sur les lignes correctes
colonne absente = zéro échec un contrôle sur une colonne manquante ne plante pas et n'invente rien
format de quarantaine les sept colonnes imposées, dans l'ordre
ligne présente plusieurs fois une ligne qui enfreint deux règles apparaît deux fois, chacune tracée
l'audit ne modifie pas les données comparaison des trois tables avant / après exécution

Le test le plus important

Le dernier de la liste mérite qu'on s'y arrête. Le brief pose comme faute éliminatoire la modification des données reçues. Plutôt que de compter sur la discipline, la contrainte devient un test : 

def test_audit_ne_modifie_pas_les_donnees(frames):
    avant = {nom: f.copy(deep=True) for nom, f in frames.items()}
    run_audit(frames, reference_date=REFERENCE_DATE)
    for nom, f in frames.items():
        pd.testing.assert_frame_equal(f, avant[nom])

Si quelqu'un ajoute un jour un contrôle qui « nettoie au passage », le test échoue immédiatement. C'est plus fiable qu'une consigne écrite dans un document que personne ne relit.

Résultat

$ pytest -q
...................................      [100%]
35 passed in 1.24s

Ces tests vont servir tout de suite. À l'étape 7, une correction apportée au registre cassera l'un d'eux — et le test aura raison contre la correction. C'est exactement ce pour quoi il a été écrit.

À retenir

Une règle silencieuse n'est pas une preuve de propreté tant qu'on n'a pas vérifié qu'elle sait parler. Tester dans les deux sens — l'anomalie détectée et la ligne saine ignorée — est ce qui rend un chiffre d'audit crédible.
